# Oracle Recruiting candidate automation: production risks

Research checked 2026-11-09. Scope: Oracle Fusion Cloud Recruiting external candidate experience driven through a browser with Playwright. This note distinguishes published product behavior from conclusions that require a tenant-specific test. OCI WAF capabilities do **not** establish that a particular career site has a WAF policy enabled.

## Documented behavior

| Area | Published fact | Practical consequence |
| --- | --- | --- |
| Candidate CAPTCHA | Oracle Recruiting supports an administrator-activated, global hCAPTCHA configuration. When enabled, the challenge appears on verification pages reached directly from the career site for **Apply to Job**, **Register for Event**, **Join a Talent Community**, **Access a Talent Profile**, and certain verification links from email. Oracle documents exceptions for an active **Keep Me Signed In** session and the optimized Apply with Indeed experience. [Oracle: Enable hCaptcha](https://docs.oracle.com/en/cloud/saas/talent-management/faimh/enable-hcaptcha.html) | A candidate can encounter a challenge when entering the apply or identity-verification flow. This source does not say one appears on every field fill, every page navigation, or final submit. |
| Candidate verification and lockout | Candidates using email or phone are authenticated with a six-digit code. Five incorrect entries lock the candidate out for 30 minutes. New candidates may verify after submitting an application; returning candidates verify before reusing their profile. Identity is generally confirmed within the same session for four hours. [Oracle: Email and SMS for Candidate Identity Verification and Communication](https://docs.oracle.com/en/cloud/saas/talent-management/faush/email-and-sms-for-candidate-identity-verification-and.html) | Login/verification is a real production dependency. The documented lockout concerns **incorrect codes**, not a published count of successful logins. |
| WAF bot controls | Oracle OCI WAF offers bot management using CAPTCHA, JavaScript, human-interaction and device-fingerprint challenges. Its WAF rate limiting can limit request frequency per unique client IP; rule configuration sets request limits, periods, action duration and actions. [Oracle: Bot Management](https://docs.oracle.com/en-us/iaas/Content/WAF/Tasks/botmanagement.htm); [Oracle: Rate Limiting for WAF](https://docs.oracle.com/en-us/iaas/Content/WAF/RateLimiting/rate_limiting_rule_management.htm); [Oracle: Add a Rate Limiting Rule](https://docs.oracle.com/en-us/iaas/Content/WAF/RateLimiting/create_rate_limiting_rule.htm) | Multiple workers behind one public IP could share a WAF rate budget **if** that tenant's site has a relevant IP rule. Oracle's general WAF documentation does not reveal the career site's actual deployment or limits. |
| Playwright behavior | `locator.fill()` waits for the field to be actionable, fills it, and fires an `input` event; `pressSequentially()` sends fine-grained keyboard events. Playwright's normal click/fill actions auto-wait for actionable elements. Headless operation is supported and is the Playwright Test default. [Playwright: Locator](https://playwright.dev/docs/api/class-locator); [Playwright: Auto-waiting](https://playwright.dev/docs/actionability); [Playwright: Configuration](https://playwright.dev/docs/test-use-options) | Fast `fill()` calls are possible. These docs make **no claim** that Oracle detects fill speed or headless mode, or that artificial typing delays prevent challenges. |
| Parallel authentication | Playwright recommends a unique account per parallel worker when tests modify server-side state. It documents reusing authenticated browser state to avoid a login for every test and warns that state files contain sensitive credentials. [Playwright: Authentication](https://playwright.dev/docs/auth) | Repeated fresh sessions and workers create extra verification traffic and possible shared-state interference; this is a Playwright testing recommendation, not an Oracle anti-bot threshold. |

## Answers to the proposed scenarios

- **Fast typing or navigation:** No official Oracle Recruiting source found here specifies a typing-speed, page-transition, or headless-browser detection rule. The credible risk is an enabled hCAPTCHA at the documented verification entry point, or a tenant-specific security control. Treat speed-based detection as an **unverified hypothesis**, not a known trigger. [Oracle: Enable hCaptcha](https://docs.oracle.com/en/cloud/saas/talent-management/faimh/enable-hcaptcha.html); [Playwright: Locator](https://playwright.dev/docs/api/class-locator)
- **Ten logins in ten minutes for one account:** No published Oracle Recruiting threshold of this form was found. Ten logins could repeatedly invoke candidate verification, but the specific documented lockout is five **incorrect verification codes** followed by 30 minutes. Do not describe ten successful logins as safe or unsafe without tenant evidence. [Oracle: Email and SMS for Candidate Identity Verification and Communication](https://docs.oracle.com/en/cloud/saas/talent-management/faush/email-and-sms-for-candidate-identity-verification-and.html)
- **Several workers on one IP:** Aggregate request volume may matter if the site's WAF has an IP-based rule; the threshold and even whether that rule exists are site-specific. Sharing one candidate identity across workers may also cause application/profile state conflicts, independently of anti-bot controls. The latter is an **inference** from Playwright's account-per-worker guidance. [Oracle: Rate Limiting for WAF](https://docs.oracle.com/en-us/iaas/Content/WAF/RateLimiting/rate_limiting_rule_management.htm); [Playwright: Authentication](https://playwright.dev/docs/auth)
- **CAPTCHA on login, fill, or submit:** The Oracle Recruiting hCAPTCHA documentation locates it on verification pages reached through specific candidate flows, including entry to **Apply to Job**. It does not promise a challenge on every login, each field fill, or final submit. A separately configured WAF policy could challenge selected requests, but that is a **capability**, not evidence of this tenant's behavior. [Oracle: Enable hCaptcha](https://docs.oracle.com/en/cloud/saas/talent-management/faimh/enable-hcaptcha.html); [Oracle: Bot Management](https://docs.oracle.com/en-us/iaas/Content/WAF/Tasks/botmanagement.htm)

## Production handling

1. Confirm the actual career site's candidate flow and hCAPTCHA setting with its administrator; measure behavior with authorized, low-volume sessions before choosing concurrency. The documentation gives no universal Recruiting login rate or CAPTCHA frequency.
2. Keep each worker's candidate/application state separate. Reuse an authorized authenticated session where the application permits it, and protect any saved browser state as a credential. [Playwright: Authentication](https://playwright.dev/docs/auth)
3. Treat CAPTCHA, OTP, lockout, and rate-limit responses as stop/hand-off or backoff conditions. Record which step and HTTP response triggered the condition; do not assume a failed automation action means a CAPTCHA, and do not retry incorrect OTPs toward the documented lockout. [Oracle: Email and SMS for Candidate Identity Verification and Communication](https://docs.oracle.com/en/cloud/saas/talent-management/faush/email-and-sms-for-candidate-identity-verification-and.html); [Oracle: Rate Limiting for WAF](https://docs.oracle.com/en-us/iaas/Content/WAF/RateLimiting/rate_limiting_rule_management.htm)
